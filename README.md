# eqoa-rust-client-vanilla: an EQOA client in Rust, without mods

A native client for *EverQuest Online Adventures: Frontiers* that owns its own data
structures, rather than running a PS2 inside a program the way
eqoa-port (the decomp as a native program) does. The goal is every platform,
phones included (wgpu: Vulkan, Metal, DX12, WebGPU), 64-bit, with the feel of the
original matched exactly.

**No game data is in this repository**, and none is downloaded: you need your own
Frontiers disc image (natively the client asks for it the first time and keeps its
place, `discs.rs`; in a checkout `run/eqoa.iso`, or `$EQOA_ISO`). What the client reads out of
the game's code modules, CLIENT (the start menu, `gWorldInfo`, the race cameras) and
SUPPORT (the HUD's atlas, the UI sounds' volumes), it reads at run time, the way
eqoa-port's gendata does. The disc holds those modules only DNAS-encrypted, so crate
`dnas` unpacks them off it with the disc's own DNAS library, on threads of their own
while the session starts, and keeps them for the next run (`eqoa-rs/dnas` in the
platform's cache directory, or `$EQOA_CACHE`; in a page, the origin's storage). The
player's decrypted images serve instead when given (`run/client.bin` or
`$EQOA_CLIENT`, `run/support.bin` or `$EQOA_SUPPORT`).

## Vanilla

The game as the PS2 plays it, with the client's own additions for a PC, a phone
or a browser (each described where it lives below):

- **Widescreen**: the HUD at a wide window's edges, the menus across it.
- **A frame rate untethered** from the game's 30 frames a second (the game's
  logic still steps at 30).
- **The mouse and the touch screen.**
- **The keyboard**, with WASD walking, and the options' **Controls** page: every
  key and button can be moved.
- **1,000 lines of chat history** (the game's ring holds 31).
- **The start menu's windows over the world**, with no green backdrop behind
  them.
- **The Extended options page**: Level of Detail, Brightness, Frame Rate, Camera
  Distance.
- **The map** (M), drawn from the player's own disc for every world, on any
  server.
- **Network Setup** on the title: the address of the server to play on (on a
  PS2 it starts the console's network utility).

## Playing a release

One build is published, **dev**: rebuilt from `master` on every push, for Linux
(x86-64), Windows (x86-64) and macOS, on the
[releases page](https://github.com/DabDavis/eqoa-rust-client-vanilla/releases/tag/dev).
Each build replaces the one before, so only the newest can be downloaded.

It is the `eqoa` program, in an archive with its README and licence, or on its
own (`eqoa-vanilla-linux-x86_64`, `eqoa-vanilla-windows-x86_64.exe`,
`eqoa-vanilla-macos`: on Linux and macOS `chmod +x` it after the download). You
need your own *Frontiers* disc image (SLUS-20744) and an account on a server
(or make one on Station's login screen, where the server allows it). Start
`eqoa` (`eqoa.exe` on Windows; `./eqoa` on Linux and macOS). The first time, it
asks for the disc image in the desktop's own file dialog, whatever the image is
called and wherever it is, checks that it is *Frontiers* (by the program its
SYSTEM.CNF starts, as the page does) and keeps its place for the next time.
`eqoa /path/to/image.iso`, or the image dropped on `eqoa.exe`, plays and keeps
that image instead, and `EQOA_ISO=/path/to/image.iso` names one for a run. The
game starts as the console does: the loading screens, the legal screen and the
licence, then the title. On the title, **Network Setup** takes the server's
address (a host name or an IPv4 address, kept for the next time); **Play**
brings Station's login screen (your account and password; Save Account keeps
both, the password in plain text, as the memory card kept them), the server's
news, the server list, character select (with creation on an empty slot) and
the world. Quitting from the start menu goes back to the server list, as on a
PS2. `eqoa boot <server>` starts with that server instead of the kept one, and
`eqoa play <server> <account>` (password in `EQOA_PASSWORD`, `EQOA_CHAR=<name>`)
goes straight into the world, for scripts. The game's options, the keys, the
server and the disc image's place (`disc.opt`, its path alone) are kept in
`eqoa-rs` in the config directory (`~/.config/eqoa-rs`, `~/Library/Application
Support/eqoa-rs`, `%APPDATA%\eqoa-rs`). On Linux it needs ALSA (`libasound2`),
libudev and a Vulkan or OpenGL driver; the file dialog is the desktop's (its XDG
desktop portal, else zenity), and where there is neither the image is named on
the command line. The builds are not
signed: the first time, macOS refuses one that came through a browser; allow it
in System Settings, Privacy & Security ("Open Anyway"), or run `xattr -d
com.apple.quarantine eqoa`. Windows' SmartScreen may ask the first time ("More
info", "Run anyway").

## Method

The language is not what makes the feel exact; the method is. Each system is ported
from the matching decomp ([eqoa-decomp](https://github.com/DabDavis/eqoa-decomp)) one at
a time and proved against a reference:

- **Game logic** (walking, camera, collision, animation) uses the EE's float model,
  crate `ee`: round toward zero, denormals flushed on the way in and out, saturation
  instead of infinity, conditioned compares, an adder with one guard bit. Every rule
  but the last was measured in a running game through the tracer (`go-eqoa-vi`); the
  tracer runs PCSX2's interpreter, whose adder keeps every bit, and the guard bit is
  PCSX2's recompiler's, which the game plays on. Rust never fuses `a*b+c` on its own,
  so written order is executed order.
- **The reference** is eqoa-port, which runs the game's own functions on the host: a
  test gives the original and the rewrite the same inputs and compares the bits.
  Until that harness exists, crates are held to the fixtures the earlier ports were.
- **Rendering** need not be bit-exact. The VU1 microcode is fully read, and eqoa-port's
  GPU strip programs already redo its maths as shaders; meshes are drawn directly with
  that maths, with no DMA, VIF or GS.

## First slice

A test of the feel before anything broad: load a zone and the player's character off
the disc, port `VIWalkControl` and `VIWalkCamera`, draw with the strip-program shaders,
and compare against eqoa-port frame by frame. If that matches, the rest is breadth:
UI, network (DRDP), sound.

### The oracle, and the two float models

The `vi` crate is written once, generic over a float model. `Ee` is the console
(crate `ee`: chop, flush, saturate, conditioned compares) and is what the client
runs. `Ieee` is eqoa-port's arithmetic (SSE single precision, no contraction,
glibc's libm), and exists for one reason: eqoa-port's `build/oracle` runs the
decomp's own functions on raw object bytes, and under `Ieee` this port must
return the same bytes. That proves the control flow, the constants and the
operation order; the `ee` crate's console goldens prove the arithmetic. The
structs are `#[repr(C)]` in the EE's layout (checked against the oracle's
`sizeof`/`offsetof` first), so nothing is translated on the way across.

```bash
(cd ../eqoa-port && make oracle)
cargo test --release -p vi        # the oracle tests skip, loudly, without it
```

The 32-bit glibc and the host's agree on `sinf`, `cosf`, `powf`, `atan2f`,
`fmodf` and `sqrtf` over 20,000 samples each (`libm_matches`), which the
comparison rests on.

### Speed

Measured in play on a local go-eqoa-server, standing in Freeport (four zones
of Tunaria, 24 creatures), i7-3770 and RX 580, with `EQOA_PERF=1
EQOA_OFFSCREEN=1280x720` (each frame's CPU time by phase, drawn on the GPU and
not presented): 4.1 ms a frame, 243 fps uncapped; it was 13.0 ms (77 fps).
What it was spent on, and what took it away:

- wgpu's command validation and tracking, 8.5 ms: every zone part a model of
  its own, ~2,700 draws and ~14,000 resources tracked at each submit. A zone
  is now one group (merged buffers, shared materials, render bundles in
  ordered runs) and a run outside the view is skipped: 1.4 ms.
- The EE float model, every game-logic operation a call: now inlined and
  branch-free, the matrix product four lanes at a time. `play` (creatures'
  poses and ground) 3.5 ms to 2.1.

In Chromium the game's thread spends 4.9 ms a frame on WebGPU (9.9 before)
and 9.4 ms on WebGL2 (25 ms and 39 fps before, wgpu's GL path being the
costlier one). The sound driver's SPU2 is under 0.4 ms of that, and natively
on a thread of its own.

The effect volumes (`EQOA_PERF`'s "volumes", `fx::bench` for the CPU alone):
0.2 ms a frame in Neriak's plaza (15 volumes rastered, 200 fans) and 1.2 ms
in the densest place found, a dust storm in zone 16 (3 volumes, 1,330
fans), most of it the EE's arithmetic placing four corners a fan
(`Matrix44::apply`, now four lanes at a time: it was 1.4 ms); in a page on
WebGL2, 0.25 ms at the local server's docks (2 volumes, 75 fans, 5 boids).
`EQOA_FX=0` (`?nofx`) leaves them out, for comparing.

### The game's frame at any display rate

The console's loop runs 30 frames a second (CLIENT's 20 ms floor, then the
raster's wait for a field); the client draws at the display's rate, 165 a
second on one tester's monitor. What the game moves by its clock (the walk
and camera in 32 ms ticks, animation, particles, the weather, the effect
volumes at most 60 steps a second) runs every frame drawn, with one difference left: the walk's damped integrator, whose
accelerations are set for the 32 ms tick, reaches a higher terminal speed
in shorter steps (running 9.07 m/s at 60 Hz and 9.26 at 165 against 8.81:
see Not yet). What it counts in frames runs on a clock of the game's frames,
30 a second (`frames.rs`): the HUD and every window (`VIKeyFlash`'s repeat
after 16 frames, `VIUIWindow` opening by 0.15 a frame, `VIUITextScroll`'s two
pixels a frame and 30-frame pause, the quick menus' light, the glows, the
"..." dots) is made once a frame of the game's and its quads drawn again in
between (`render::ui::Ui::keep`/`again`); the damage numbers are laid out
then (their `rand()`s are the game's) and placed through every view drawn;
`TrackTarget`'s colour easing, `DeathCamera`'s swing and `VICameraEffect`'s
shake samples step on it too. Run every frame at 165 Hz they went 5.5 times
as fast: the target's name rocked at 330 pixels a second with 0.18 s pauses
(the console's 60 and 1 s), the menus' first repeat came after 97 ms (533).
`frames.rs`'s tests drive the repeat, the name's scroll and the rings at 30,
60, 144 and 165 Hz against the console's times, each with its control. A key
let go before its first pulse still fires once (a keyboard's tap can fall
between two of the game's frames; a pad read once a frame cannot), and a
finger's drag pushes the stick for a sixtieth of a second a pixel, whatever
the rate (the mouse turns by its own motion, an angle a pixel, and the
follow orbit's way back out after a pull runs by the clock).
`EQOA_FRAME_MS=n` gives a `shot` or `playshot` frames n ms long.

### The dictionary

The game keeps one dictionary per stage, and every file it loads registers into
it; a record whose DictID is already present is skipped, so **the first file
loaded wins** (`ParseSurfaceObj` finds before it adds; `VIMap::Insert` keeps an
existing key). It matters: CHAR.ESF and CHARCUST.CSF share 16 DictIDs and 8 of
them carry different bytes (`cargo run --release -p eqoa --example dict_overlap`).
GroupSprite members are read as the decomp reads them, (angles, scale,
translation), not as the Go tools do (`claude-notes/groupsprite-member-order-20261019.md`).
Which records register is read off the decomp's 27 `m_dict->Add` sites, not off
the Go tools, whose table missed point sprites (all 362 of ITEM.ESF's
unresolved GroupSprite members) and registered version-0/1 PrimBuffers. A scene
loads its own file first, then CHARCUST.CSF and CHARFACE.CSF; the game's real
order per stage is not yet measured.

- Baked lighting is drawn for placed actors (a lit actor draws its own copy with
  its colour buffers; LOD sprites draw level 0, which takes the first) and the
  static colour per instance, but not checked against the console yet. The personal light (the lantern, `vi::tod::PersonalLight`,
  ramped as `SetupTimeOfDayLights` does) is the strip programs' point term;
  lighting is per vertex as VU1's (the game also tessellates near the point
  light, which is not done here). The two passes are the scene's: a material whose
  first layer is opaque draws whole at once, one whose first layer blends is
  deferred whole (`MaterialHasDepthSort`); the deferred pass runs in model
  order, not the game's tree-walk order (rooms, flora, actors).
- Zone streaming is `VIWorld::StreamLeaf`'s radial rule (load within 900 of a
  zone's bounds, let go past 950, a zone a frame, all at once under the loading
  screen) for drawing only: collision still loads the whole file (two seconds for
  Tunaria), and `VIZone::Stream`'s finer per-static radii (500/550) are not ported.
- A lighting band along terrain patch edges (zone 84 at x = 25000): not a gap,
  the edges' vertex colours or normals; to revisit with the real lighting.

## In a browser

The same client builds for `wasm32-unknown-unknown` and runs in a page
(`web/`): WebGPU where the browser has a working adapter, else WebGL2 (the
renderer asks for nothing WebGL2 lacks, and the adapter there is the canvas's
own, so the device is made on the page's canvas before the event loop). A
page on WebGL2 draws 30 frames a second (`web::frame_due`: an animation frame
before the next is due is skipped whole, the game's clocks seeing longer
frames; the options' Frame Rate, or `?uncapped`, lifts it). The
player picks their own disc image in the page; it is read there a slice at a
time (`File.slice`), never uploaded, and nothing from it is served. What the
game reads synchronously is fetched first; whatever walks the image (its
directory, a world file's record headers) runs against `iso::Sparse`, a cache
that answers `WouldBlock` for bytes it lacks and is filled between attempts
(`tests/sparse.rs`: the listing in 2 fetches, 128 KB, equal to the file's).

The page asks only for the player's disc image (the gate; the relay and the
offline viewer are folded under "Server and viewer"); Start runs the game from
its boot on the canvas, as natively: the loading screens, the licence, the title,
Station's login screen (sign-in and Create User Name are the game's own pages),
the news, the server list, character select and creation, the world. The
pregame's files are read off the image as each stage asks for them
(`pregame::files`), the world entry's in `world_library`'s order on a reader of
their own. A page can open neither a UDP socket nor a TCP connection, so the
session's datagrams (`net::session::Datagrams`: a UDP socket natively), Station's
connection (its login, account creation and password change) and the news
page's HTTP go through a relay, behind the pregame's `link`: go-eqoa-server's
`cmd/wsrelay`, which speaks eqoa-port's `tools/wsrelay.py` protocol, one
WebSocket for the DRDP datagrams and one per TCP connection (the relay must
reach the server's ports 9735 and 7000 for them). A server named by host name in
Network Setup is resolved by the relay; with none set, the page's own host is
the server. A world opens with its zones left on the disc and the ones round
the player read before the walk starts (`stream::fill_set`, awaited), the rest
as the walk comes near them (`web::disc::WebZones`, a `stream::ZoneSource`
whose reads finish on a later frame): in Freeport at the display's rate, 60
fps in Chromium, with 248 MB of wasm heap (the whole file read was 1.8 GB).
A world change (a teleport into another world, 0x00B2) is the same reads
(`stream::open_world`: the world file opened on a reader of its own and the zones
round the arrival read) while the old world plays on under the loading screen,
then the walk begins again there on the frame they are in: Lavastorm in 21-35 ms,
Tunaria with four zones in 260-400 ms, and back to 60 fps a second later. The
game's clock runs on through it, as VITimer does (the viewer used to restart it,
which put the creatures' animations before their start and panicked on a frame
of -1).

The start menu reads CLIENT's data and the HUD SUPPORT's, which the disc holds only
encrypted. The page unpacks both off the player's disc with `dnas`, each in a Web
Worker of its own (`web/unpack.js`) that instantiates the same compiled module, so
the game's thread never runs them: they start as soon as the disc is open and take
1.9 s and 2.7 s in Chromium, side by side (5.9 s and 6.3 s before the natives), and the frame rate stays at 60 while
they run. What they unpacked is kept in the origin's private storage (OPFS) under
the SHA-256 of `UTIL.REL` and the `.AUT`, so a later visit has both at once (a
page without `crypto.subtle`, plain http to another host, unpacks them every time).
On a first visit the HUD and the start menu come when they do, a few seconds into
the world if it was entered quickly.

```bash
cargo install wasm-bindgen-cli --version 0.2.129   # once: the version Cargo.lock pins
web/build.sh                                        # web/dist: the page, version.json and the build, v/<build>/
EQOA_WEB_DEST=user@host:/path/to/play/ web/deploy.sh
web/pagetest.py --iso run/eqoa.iso                  # the page's updates, notices and crashes
web/drive.py --iso run/eqoa.iso --view 'CHAR.ESF 0x70D898C6' --shot 6=human.png   # headless Chromium
web/drive.py --base https://host/eqoa/play/ --iso run/eqoa.iso --boot --keys 13=ArrowRight:100 \
    --keys 13.6=Enter:100 --keys 17=Enter:100 --type 21=<user> --shot 30=station.png
```

Each build is a directory of its own, `v/<build>/`, named by the digest of its files,
the page and the commit (`web/build.sh`), so nothing under that name ever changes: the
host serves `v/` as immutable and revalidates only the page and `version.json`.
`web/deploy.sh` publishes the build's directory first, then the page that names it, then
`version.json`. Builds stay two days, and the newest three always, for the pages still
running them: a page fetches its worker and its worklet a while after it opened. A page
already open asks for `version.json` every minute and whenever it is shown again. On the
gate with no disc picked it reloads at once; anywhere else it says a new version
is out and the player reloads when it suits them; a reload that brings the old page back
is a problem notice, not another reload. Until 2026-10-20 a deploy rewrote the files in
place one at a time: a page loaded during one could mix two builds (a tester's did, to
the second), and a tab left open never heard of a new build.

What goes wrong is said on the page (`web/notices.js`), and nothing is sent anywhere.
A panic, a wasm trap or a lost graphics device stops the client: the canvas would keep
its last frame, so the page says so, with a Reload. What only takes a part away is a
notice with a Dismiss: a disc other than Frontiers, named by the program it starts as soon as it is picked (`web/disc.rs`;
with the European discs and the Frontiers beta there is no HUD and no start menu, with
the first USA disc and the 2002 betas no world: each measured through the page), a
module that would not unpack on the Frontiers disc (unpacked once more past the page's
copy first), a file of the page that did not load, no sound, a failed world change.
`web/pagetest.py` checks the page's half: the update paths, a panic's notice and its
Reload, F3 opening nothing, nothing posted, a page whose build is gone, the disc line.
Each check has its control. `drive.py --scale`
is the display's own scale: at Windows' 125% and 150%, on WebGPU and on WebGL2, the HUD
draws as at 100% and the canvas holds the device's pixels.

F11 is the browser's own full screen. The canvas cancels every key it is given
(winit's listener calls `preventDefault`), which kept F11 from the browser, so the
page catches F11 on its way down and leaves it to the browser (`web/main.js`); the
canvas follows the window's size, and the HUD its shape. Checked with
`drive.py --headed` on an Xvfb with a window manager, F11 pressed through X (the
page 1192x609, then the screen's 1600x900, then back, the canvas's buffer each
time), and with `--resize` (the game at 60 fps after each new size).

The page takes `?relay=` and `?server=` (an IPv4 address; by default the
page's own host, as the relay resolves it), `?webgl` for WebGL2 where
WebGPU works (the same frame, 60 fps in Chromium through ANGLE) and `?padtrace`
(each pad key and gamepad event in the console). Not in the browser yet: a 3D
preview on the character screens; CHAR.ESF (148 MB) is still read whole.

A gamepad works in a page as natively (the page reads the Gamepad API itself,
`padmap`: every button and axis, and the layout each browser gives, Firefox on
Linux's own for an Xbox pad included; a pad shows up after its first button press,
as browsers expose them; `?padxy=swap` or `?padxy=keep` for a pad whose X and Y
the rule gets wrong), its
motors through the API's dual-rumble (`window.eqoaRumble`, main.js). On a phone or a
tablet (a page whose pointer is coarse, `window.eqoaTouchFirst`) the touch screen's
pad is there from the start. `drive.py` plays them: `--gamepad SECONDS=STEPS` (a
scripted pad behind `navigator.getGamepads`), `--mobile` (CDP's touch emulation),
`--touch SECONDS=STEPS` (CDP touch events on the canvas) and `--mouse SECONDS=STEPS`
(clicks, right clicks, the wheel, drags with either button, buttons held across steps). A
right click reaches the game: winit keeps the canvas's context menu shut. A drag in play
takes the Pointer Lock (asked for in the pointer's move past the slop, inside the press's
transient activation; after two refusals running, in the press), which headless Chromium
grants to CDP's mouse events; a browser keeps Escape to end its lock (the page sees it
gone), and an Escape that reaches the page lets go as well.

The sound is the native client's. A page can give the driver no thread of its own,
so it runs on the game's: once a frame (and at each animation frame a 30-fps page
skips) it is mixed up to the page's audio clock plus a lead and the frames are handed
to an AudioWorklet (`web/sound.js`) that only plays them, at 48 kHz (resampled where
the context will not run at that rate). The lead is what a sound the game starts
waits before it is heard, so it is sized by how far the audio clock moved between two
feeds over the last ten seconds (`audio::lead_for`: the third largest move, half again
and 5 ms, 30-300 ms); the clock moves in the blocks the browser's output takes (10.7
ms in Chromium, 30 in Firefox on Linux). Key to the worklet, in the world: 53-61 ms
median where it was 76-100 (and 150 in Firefox's first minute, its lead at 200). A
feed later than the lead leaves a short gap and pauses the driver for it, so nothing
is skipped. The AudioContext is made on the click that starts
the game (Start), as a page may only start sound from its user's gesture. The streamed music is read
whole off the disc (7 to 9 MB, 40-190 ms in Chromium) before the device starts it,
and the last three files are kept. In Chromium, in Freeport: 60 fps with the sound,
the region's music read and playing, no underrun after the world's first frames; the
status line shows the lead and the underruns, and `eqoaAudio.stats()` the worklet's
counts and level.
