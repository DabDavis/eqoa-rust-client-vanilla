# eqoa-rust-client-vanilla: an EQOA client in Rust, without mods

A native client for *EverQuest Online Adventures: Frontiers* that owns its own data
structures, rather than running a PS2 inside a program the way
eqoa-port (the decomp as a native program) does. The goal is every platform,
phones included (wgpu: Vulkan, Metal, DX12, WebGPU), 64-bit, with the feel of the
original matched exactly.

**No game data is in this repository**, and none is downloaded: you need your own
Frontiers disc image (natively the client asks for it the first time and keeps its
place, `discs.rs`; in a checkout `run/eqoa.iso`, or `$EQOA_ISO`). What the client reads out of
the game's code modules, CLIENT (the start menu, `gWorldInfo`, the race cameras) and
SUPPORT (the HUD's atlas, the UI sounds' volumes), it reads at run time, the way
eqoa-port's gendata does. The disc holds those modules only DNAS-encrypted, so crate
`dnas` unpacks them off it with the disc's own DNAS library, on threads of their own
while the session starts, and keeps them for the next run (`eqoa-rs/dnas` in the
platform's cache directory, or `$EQOA_CACHE`; in a page, the origin's storage). The
player's decrypted images serve instead when given (`run/client.bin` or
`$EQOA_CLIENT`, `run/support.bin` or `$EQOA_SUPPORT`).

## Vanilla

or a browser (each described where it lives below):

  closed at its edges.

  logic still steps at 30).
- **The mouse and the touch screen.**
- **The keyboard**, with WASD walking, and the options' **Controls** page: every
  key and button can be moved, and a controller's button can take any of the
  keyboard's own actions (Hide UI, F9's art).
- **1,000 lines of chat history** (the game's ring holds 31).
- **The start menu's windows over the world**, with no green backdrop behind
  them.
- **The Extended options**, a page for each of Video (Display: a window or full

  column with ○ (C on the keyboard) or a click on its heading (the game keeps
  the server's order).
- **Network Setup** on the title: the address of the server to play on (on a
  PS2 it starts the console's network utility).
- **Updates**: a downloaded build puts the release's newer one in its place
  as it starts, before the title.
- **Problem and crash reports**: F3, or the HUD's Report a bug, sends a note
  and a picture of the screen to the report board; the crashes since are offered
  to be sent at the next start, all in one. Nothing is sent unless the player
  says so.

## Playing a release

One build is published, **dev**: rebuilt from `master` on every push, for Linux
(x86-64), Windows (x86-64) and macOS, on the
[releases page](https://github.com/DabDavis/eqoa-rust-client-vanilla/releases/tag/dev).
Each build replaces the one before, so only the newest can be downloaded; the
release page's update notes (`UPDATE-NOTES.md`) say what each build changed.

The program's icon is a drawn disc of its own (`icon_art.rs`: no game art; the
Windows `.exe` carries it in its resources, made by `build.rs` from the same
drawing, and the pages have it as `web/disc.svg`) until it has read the
player's disc image; from then on it is the game's own memory card icon, the
3D head a PS2's browser showed for the save, drawn from SUPPORT's
`VIMemCardIconData` on the player's disc (`saveicon.rs`) and kept as
`saveicon.png` in the config directory, so the next start with that disc opens
with it (`icon.rs`: the window under Windows and X11, the Dock on a Mac;
Wayland shows a program's icon only through a desktop entry, for which the
Linux archive carries `eqoa.png`). `eqoa icon <size> <out.png> [save]` writes
either.

It is the `eqoa` program, in an archive with its README and licence, or on its
own (`eqoa-vanilla-linux-x86_64`, `eqoa-vanilla-windows-x86_64.exe`,
`eqoa-vanilla-macos`: on Linux and macOS `chmod +x` it after the download). You
need your own *Frontiers* disc image (SLUS-20744) and an account on a server
(or make one on Station's login screen, where the server allows it). Start
`eqoa` (`eqoa.exe` on Windows; `./eqoa` on Linux and macOS). The first time, it
asks for the disc image in the desktop's own file dialog, whatever the image is
called and wherever it is, checks that it is *Frontiers* (by the program its
SYSTEM.CNF starts, as the page does) and keeps its place for the next time.
`eqoa /path/to/image.iso`, or the image dropped on `eqoa.exe`, plays and keeps
that image instead, and `EQOA_ISO=/path/to/image.iso` names one for a run. The
game starts as the console does: the loading screens, the legal screen and the
licence, then the title. On the title, **Network Setup** takes the server's
address (a host name or an IPv4 address, kept for the next time); **Play**
brings Station's login screen (your account and password; Save Account keeps
both, the password in plain text, as the memory card kept them), the server's
news, the server list, character select (with creation on an empty slot) and
the world. Quitting from the start menu goes back to the server list, as on a
PS2. `eqoa boot <server>` starts with that server instead of the kept one, and
`eqoa play <server> <account>` (password in `EQOA_PASSWORD`, `EQOA_CHAR=<name>`)
goes straight into the world, for scripts. The game's options, the keys, the
server and the disc image's place (`disc.opt`, its path alone) are kept in
`eqoa-rs` in the config directory (`~/.config/eqoa-rs`, `~/Library/Application
Support/eqoa-rs`, `%APPDATA%\eqoa-rs`). Several windows open at once each read
their own controller (the first window the first; the Extended page's Controller
Focus picks another, the same for several, or the window in front; on Windows a
controller that is not an Xbox one, or passed off as one, reaches only the window
in front). On Windows `eqoa.exe` opens no console window: started from a terminal,
its messages print there. On Linux it needs glibc 2.34 or newer
(Ubuntu 22.04, Debian 12, Fedora 35 or later), ALSA (`libasound2`), libudev and a
Vulkan or OpenGL driver; the file dialog is the desktop's (its XDG
desktop portal, else zenity), and where there is neither the image is named on
the command line. On a Steam Deck in Steam's Game Mode (gamescope, which shows
no desktop portal's window) a disc not known or not there (one kept on a USB
drive, which Game Mode does not mount) is first looked for where a Deck keeps
its games (the home folder and its Downloads, Desktop, Documents, Games and ROMs
folders, EmuDeck's `Emulation/roms/ps2`, and the same on the microSD card under
`/run/media`, a folder down), then asked for in zenity's dialog. The builds are not
signed: the first time, macOS refuses one that came through a browser; allow it
in System Settings, Privacy & Security ("Open Anyway"), or run `xattr -d
com.apple.quarantine eqoa`. Windows' SmartScreen may ask the first time ("More
info", "Run anyway").

**The 2002 art.** With your own *EverQuest Online Adventures* (USA) disc image
of 2002 (SLUS-20470) beside the *Frontiers* one, **F9** (or Options > Extended >
Art) draws the game as it looked then, anywhere from the loading screens to the
world; F9 again goes back. The first time, F9 at the title or at character
select asks for that image in the file dialog and keeps its place
(`disc2002.opt`), and the choice is kept too (`EQOA_2002_ISO=/path/to/image.iso`
names one for a run). In the world it says so in the chat instead: the dialog
holds the window while it is open, and a server lets a silent session go within
seconds. Without the disc nothing changes: a kept image that is gone counts as
none, and one that does not open leaves Frontiers' world. The European discs of
2003 already carry nearly all of Frontiers' art and the 2002 betas lay their
files out apart, so only the USA disc is taken. What only Frontiers has (its new
creatures and worlds, its new icons) stays as Frontiers draws it.

**A downloaded build updates itself.** As it starts (`eqoa`, `eqoa boot`, `eqoa
<image>`), a thread reads the release's `update.txt`, which the release's build
writes beside its programs: the commit it was built from, and each platform's
program with its SHA-256 and size. When the commit is not this build's, the
program is downloaded beside this one, held to that hash and size, and put in
its place by two renames (this one aside as `eqoa.old`, which the next start
removes; on Windows, while another window of the game still runs the one the last
update set aside, which nothing may remove or replace, as `eqoa.old-1` and on); the
boot's loading picture says how far the download is, and before
the title the window closes and the new build starts in its place, with the
same arguments. A build made anywhere but the release's CI carries no channel
and never updates itself; `EQOA_NO_UPDATE=1` leaves a release's build as it is
for a run, and a failure (no network, a folder it may not write to, a download
that is not the one named) is said in the log and the game plays on. While the
game runs it asks the release again (three minutes after the start, then every
ten; the release, not the game server, so on any server), puts a newer build in
place the same way, and asks the player whether to restart now in a window of
the game's own that lists what is new in it (the sections of the release's
update notes this build's own lack, every version's since if several came out),
once nothing else is on the screen, nothing is being typed and the controls have
been let go a moment: Restart now leaves the world as Quit does and starts the
new build; Later (the choice it starts on) asks again in half an hour. A page
asks the same of its player (Reload / Later), with what is new in it.

**Problems are reported from the game.** F3, or the HUD's **Report a bug** under
the target's bar, opens a dialog over the game (over the screens before the world
too): what happened, a name to be credited by on the board (Tab), Send (Enter) or
Close (Escape). It sends the note, a picture of the screen, the client's state
(the character, the world, the creatures round it, the options, the keys and
controllers) and the log's last 200 lines to the report server; its board,
[eqoaclassic.com/eqoa/reports/board](https://eqoaclassic.com/eqoa/reports/board),
shows the note and the picture and never the rest. The account name and the
password are taken out of everything sent, as is the home directory's path. The
program's messages are kept in `eqoa.log` in the config directory (the run before
as `eqoa.prev.log`; a second window open beside the first keeps `eqoa-2.log`, and
so on); a frame that came a second or more after the last is one of them
(`stall.rs`: how long, when in UTC, the frame's longest phases or the time outside
it, the game's waits for the sound's driver, the disc's slowest read, the game
server's last datagram), and a report carries another window's as it does its
focus lines. When the game stops on a fault it writes a crash report into
`crashes/` there, and a run that ended without closing (killed, or stopped where
nothing could write one) is found by the next start in the log it left; the next
start offers everything waiting in one (Send, Not now or Delete; Send all and
Delete all when there are several; the newest five are kept), saying how many,
how long ago the game last stopped and, when one was another version, which.
Nothing is sent unless the player presses Send.

## Method

The language is not what makes the feel exact; the method is. Each system is ported
from the matching decomp ([eqoa-decomp](https://github.com/DabDavis/eqoa-decomp)) one at
a time and proved against a reference:

- **Game logic** (walking, camera, collision, animation) uses the EE's float model,
  crate `ee`: round toward zero, denormals flushed on the way in and out, saturation
  instead of infinity, conditioned compares, an adder with one guard bit. Every rule
  but the last was measured in a running game through the tracer (`go-eqoa-vi`); the
  tracer runs PCSX2's interpreter, whose adder keeps every bit, and the guard bit is
  PCSX2's recompiler's, which the game plays on. Rust never fuses `a*b+c` on its own,
  so written order is executed order.
- **The reference** is eqoa-port, which runs the game's own functions on the host: a
  test gives the original and the rewrite the same inputs and compares the bits.
  Until that harness exists, crates are held to the fixtures the earlier ports were.
- **Rendering** need not be bit-exact. The VU1 microcode is fully read, and eqoa-port's
  GPU strip programs already redo its maths as shaders; meshes are drawn directly with
  that maths, with no DMA, VIF or GS.

## First slice

A test of the feel before anything broad: load a zone and the player's character off
the disc, port `VIWalkControl` and `VIWalkCamera`, draw with the strip-program shaders,
and compare against eqoa-port frame by frame. If that matches, the rest is breadth:
UI, network (DRDP), sound.

### The oracle, and the two float models

The `vi` crate is written once, generic over a float model. `Ee` is the console
(crate `ee`: chop, flush, saturate, conditioned compares) and is what the client
runs. `Ieee` is eqoa-port's arithmetic (SSE single precision, no contraction,
glibc's libm), and exists for one reason: eqoa-port's `build/oracle` runs the
decomp's own functions on raw object bytes, and under `Ieee` this port must
return the same bytes. That proves the control flow, the constants and the
operation order; the `ee` crate's console goldens prove the arithmetic. The
structs are `#[repr(C)]` in the EE's layout (checked against the oracle's
`sizeof`/`offsetof` first), so nothing is translated on the way across.

```bash
(cd ../eqoa-port && make oracle)
cargo test --release -p vi        # the oracle tests skip, loudly, without it
```

The 32-bit glibc and the host's agree on `sinf`, `cosf`, `powf`, `atan2f`,
`fmodf` and `sqrtf` over 20,000 samples each (`libm_matches`), which the
comparison rests on.

### Speed

Measured in play on a local go-eqoa-server, standing in Freeport (four zones
of Tunaria, 24 creatures), i7-3770 and RX 580, with `EQOA_PERF=1
EQOA_OFFSCREEN=1280x720` (each frame's CPU time by phase, drawn on the GPU and
not presented): 4.1 ms a frame, 243 fps uncapped; it was 13.0 ms (77 fps).
What it was spent on, and what took it away:

- wgpu's command validation and tracking, 8.5 ms: every zone part a model of
  its own, ~2,700 draws and ~14,000 resources tracked at each submit. A zone
  is now one group (merged buffers, shared materials, render bundles in
  ordered runs) and a run outside the view is skipped: 1.4 ms.
- The EE float model, every game-logic operation a call: now inlined and
  branch-free, the matrix product four lanes at a time. `play` (creatures'
  poses and ground) 3.5 ms to 2.1.

In Chromium the game's thread spends 4.9 ms a frame on WebGPU (9.9 before)
and 9.4 ms on WebGL2 (25 ms and 39 fps before, wgpu's GL path being the
costlier one). The sound driver's SPU2 is under 0.4 ms of that, and natively
on a thread of its own.

The effect volumes (`EQOA_PERF`'s "volumes", `fx::bench` for the CPU alone):
0.2 ms a frame in Neriak's plaza (15 volumes rastered, 200 fans) and 1.2 ms
in the densest place found, a dust storm in zone 16 (3 volumes, 1,330
fans), most of it the EE's arithmetic placing four corners a fan
(`Matrix44::apply`, now four lanes at a time: it was 1.4 ms); in a page on
WebGL2, 0.25 ms at the local server's docks (2 volumes, 75 fans, 5 boids).
`EQOA_FX=0` (`?nofx`) leaves them out, for comparing. On the GPU
(`fx::bench::fans_cover`, `EQOA_FX_SPOT=<world>,<x>,<y>,<z>,<hour>`: a spot's
fans laid on a 1000x1000 screen from a camera 3.3 behind at 15 degrees, the
ground hiding what is under it, then drawn over the ground's depth): at
Klick'Anon after midnight (F3 crashes 20261026-233805/6: two 50 x 3.7 x 50
night-fog boxes of 150 puffs each, 298 fans, which is no cap) 1.0 to 1.9
screens of fragments, the deepest pixel under 40 puffs, 0.10 ms on the RX 580
(1.3 whole-screen blended layers); Odus's same pair at most 3.7 screens, 0.19
ms; the dust storm's 1,325 fans 1.8 screens. The console draws the same fans
(`VIEffectVolume`'s counts, fades and hours; `VIRFan` drops only the back face
and what lies wholly outside a clip plane), into a 640x448 frame.

### The game's frame at any display rate

The console's loop runs 30 frames a second (CLIENT's 20 ms floor, then the
raster's wait for a field); the client draws at the display's rate, 165 a
second on one tester's monitor. What the game moves by its clock (the walk
and camera in 32 ms ticks, animation, particles, the weather, the effect
volumes at most 60 steps a second) runs every frame drawn, all but the walk,
which keeps the console's own frames (`walker.rs`, `Kept`): its damped
integrator's accelerations are set for the 32 ms tick, so stepped once a frame
drawn it reached a higher top speed in shorter steps (a run on flat ground 9.11
m/s at 60 Hz and 9.30 at 165 against 8.85, a turn 6% faster), and at Tunaria's
places each frame's add was also cut to the floats' step, so the speed shifted
with the rate and the heading too. Each frame drawn now puts the walk back to the
last console frame (two fields, 33.37 ms), steps the console frames come since
as the console steps them (`Process`: a tick and the rest), and draws that frame
on its way to the next (`Process` on a copy, on the frame's controls): the place,
heading, pitch and height offset as far along as the frame drawn is, in doubles,
the rest (floor, water, locomotion) as the console frame has it. Its tests keep
every console frame bit for bit as a console at 29.97 frames a second does, at
60, 165 and 240 Hz and with frames 1.5 ms early or late; the run drawn moves every
frame and is as straight as the console's own frames to within a float step
(1.95 mm at x 22000); a place given between frames, a landing, the camera's
no-turn flag and a stall each have theirs, each with its control. The mouse's
look, which turns the body at once (the client's own), is made on the kept frame
(`Walker::rewind` first, once a frame), as a control: made on the frame drawn it
read as a place given, and while the mouse moved no console frame was stepped
(the run from a stand crept, a run let go of slid on, slopes sank it and floated
it). The place that look gives the follow orbit's camera (behind the body, or
round it) is then moved onto the walk as last drawn (`Walker::camera_as_drawn`),
where the camera's `Process` would find it with the keys alone: left round the
kept frame, a sidestep put the body drawn off the camera's line, and the camera
swung 0.7 to 4 degrees round it and back at the console's rate (the eye jumped
0.2 a frame at 144 Hz, against 0.012 with the keys alone). `Process` runs
twice a console frame (the frame, and the one ahead again when the controls
change), so the walk costs about what it did at 144-165 Hz, half at 240 and up to
twice at 60 (0.1 ms a frame more). What it counts in frames runs on a clock of the game's frames,
30 a second (`frames.rs`): the HUD and every window (`VIKeyFlash`'s repeat
after 16 frames, `VIUIWindow` opening by 0.15 a frame, `VIUITextScroll`'s two
pixels a frame and 30-frame pause, the quick menus' light, the glows, the
"..." dots) is made once a frame of the game's and its quads drawn again in
between (`render::ui::Ui::keep`/`again`); the damage numbers are laid out
then (their `rand()`s are the game's) and placed through every view drawn;
`TrackTarget`'s colour easing, `DeathCamera`'s swing and `VICameraEffect`'s
shake samples step on it too. Run every frame at 165 Hz they went 5.5 times
as fast: the target's name rocked at 330 pixels a second with 0.18 s pauses
(the console's 60 and 1 s), the menus' first repeat came after 97 ms (533).
`frames.rs`'s tests drive the repeat, the name's scroll and the rings at 30,
60, 144 and 165 Hz against the console's times, each with its control. A key
let go before its first pulse still fires once (a keyboard's tap can fall
between two of the game's frames; a pad read once a frame cannot), and a
finger's drag pushes the stick for a sixtieth of a second a pixel, whatever
the rate (the mouse turns by its own motion, an angle a pixel, and the
follow orbit's way back out after a pull runs by the clock).
`EQOA_FRAME_MS=n` gives a `shot` or `playshot` frames n ms long.

### The dictionary

The game keeps one dictionary per stage, and every file it loads registers into
it; a record whose DictID is already present is skipped, so **the first file
loaded wins** (`ParseSurfaceObj` finds before it adds; `VIMap::Insert` keeps an
existing key). It matters: CHAR.ESF and CHARCUST.CSF share 16 DictIDs and 8 of
them carry different bytes (`cargo run --release -p eqoa --example dict_overlap`).
GroupSprite members are read as the decomp reads them, (angles, scale,
translation), not as the Go tools do (`claude-notes/groupsprite-member-order-20261019.md`).
Which records register is read off the decomp's 27 `m_dict->Add` sites, not off
the Go tools, whose table missed point sprites (all 362 of ITEM.ESF's
unresolved GroupSprite members) and registered version-0/1 PrimBuffers. A scene
loads its own file first, then CHARCUST.CSF and CHARFACE.CSF; the game's real
order per stage is not yet measured.

### The 2002 art

`era.rs`, `esf::Library`'s 2002 view, `render::TextureSource` keys; measured file
by file in `../claude-notes/era-2002-art-20261024.md`. The two discs name their art
alike (a DictID is the hash of the art's name), so a file off the 2002 disc **stands
in** for its Frontiers namesake (`Library::stand_in`): it registers in a second
dictionary just ahead of it, and lookups answer from that one while the library's
view is 2002's (`set_view`, `with_view`). What the 2002 disc lacks (Frontiers' new
creatures and worlds, its new icons) is still found in Frontiers' files. A 2002
record byte for byte its namesake's is registered as that record (worked out once
per pair, `same_as_namesake`), so what did not change stays one texture and one
model; ITEM.ESF, the arena, Arial and the sounds are the same on both discs.

- **A model is built whole in one view** (`Library::view_for`): one the 2002 disc
  has, out of the 2002 dictionary; one only Frontiers has, out of Frontiers'
  records alone (8 of Frontiers' 171 new creatures name an animation or a texture
  whose 2002 namesake differs). A creature remembers the view it was built in and
  is made again when the art turns; so are the player's body, the HUD's layer,
  the rings, the gears, the spell effects and the sky.
- **Textures are cached by record**: the renderer keys a texture by its DictID and
  whether its record is off the 2002 disc (`Library::texture_key`).
- **The HUD atlas stays Frontiers'** (`era::kept`): SUPPORT's table cuts its rects
  out of UI.CSF's `sheet1`, and the 2002 sheet is laid out otherwise where
  Frontiers added art; the windows' tiles, the icons and the font come over
  (`UiAssets::add_surfaces_of` takes a 2002 file's surfaces only where the view
  answers with it).
- **Tunaria comes off the 2002 disc** (`era::world_era`; the other worlds are
  Frontiers' always): the same ground, its own baked lighting, a few props
  otherwise. Its zone list is an older format (record 0x8210 version 1, each
  zone's entry followed by its name). F9 swaps it under the walk
  (`viewer::swap_world_art`, `stream::reopen`): the zones round the player read
  off the other disc and drawn, the collision world, particles, effect volumes
  and the sound's world made again, the walk where it was (150-260 ms
  natively).
- **With Frontiers' additions**: the 2002 disc's zones place no effect volumes
  (fog, dust, leaves, shafts, flocks) and no streamed audio; Frontiers' Tunaria is
  kept as its twin (`Library::set_twin`, its zones left on the disc), each zone is
  read with its twin's (`stream::Twinned`), and what the twin's zone places of
  those two kinds, with the records they name, goes into the 2002 zone's rooms
  after its own (`Container::additions`, `Library::add_zone_extras`; the rooms
  match on both discs). Round the Freeport spawn: Frontiers' 102 placements, each
  at its place.
- **Before the world**, the pregame reads each art file's 2002 copy beside the
  disc's (`era::read`) and waits for both: the loading pictures (2002's in
  DATA2), the title's painting with the original game's effects layer, Station's
  and the server list's blue stone, character select and creation with 2002
  figures, CLIENT's loading screen in the original layout. F9 there makes again

  the 2002 disc's theme in its art.
- **The disc**: judged by its SYSTEM.CNF and its DATA2 (`era::judge`), natively
  picked in the file dialog the first time F9 or the Art row asks before the world
  (in the world the chat says where: a modal dialog holds the session's loop,
  `viewer::ask_disc`), kept in `disc2002.opt`; in a page, the form's second input,
  whose picker holds nothing. The choice is `client.opt`'s `art=2002`; it is in
  effect only with the disc at hand (`era::current`; a kept path that is gone is
  none), and a 2002 world that does not open is Frontiers' (`stream::open_world`,
  world entry).
- Tests: `EQOA_2002_ISO=<image>`, and `EQOA_ART_AT=<ms>;<ms>` presses F9 in a
  scripted run.

  jumped to: `net::session::SyncTime`), and the hour is clock B's, modulo
  3,600,000 of its units as 24 hours (`Session::time_of_day`); before any 0x0013,
  and with no server, it runs from 10:00 at 24 h per hour; `EQOA_HOUR` pins it.
  The fog's distances are `CalcTimeOfDayClipPlanes`', and the far one is the
  camera's far plane (`CalcFarPlane`, `Grid::far_plane`: `VIWalkCamera::SetCamera`
  hands it `VICamera::Init` each frame), so nothing past the fog is drawn; the
  sky keeps a far plane of its own (`fog.rs`). The table, the profiles, the
  blend and the clip planes are held to the oracle (ops 600, 601, 1500); the
  Lights/Fog/Sky functions that combine them write the raster, so they are not.
- The sky and the weather (`eqoa/src/weather.rs`, `sky.rs`): the atmosphere
  is held to the oracle; in the client its two rays go through the scene's
  ray walk, the fireballs ride their own particle system, and the stars and lightning
  patches are drawn after the world at the far plane (the game draws them
  before it with Z off), which differs only behind a blended surface.
  `EQOA_WEATHER=t[,fade]` sets the weather in `shot`, `view` and `listen`;
  the server sets it with 0x00C5 (fade) and 0x00C7 (instant), taken in the
  messages' order with the sky set at once where a port or a dump left the
  player (`play::Atmos`, `Weather::take`: `Respawn` and `Msg000D` end with
  `SetSky(m_camera, 1)`; another world's waits until it is entered). Before,
  only the first frame set the sky at once, and every port faded it over 30 s
  with the weather held behind it (F3 20261024-090748: two windows sent the
  same eight changes on Sandstorm, 80 ms apart, took them alike standing
  still). A problem report gives the atmosphere's state (`Weather::describe`)
  and each `play: weather` line the server's hour.
- Baked lighting is drawn for placed actors (a lit actor draws its own copy with
  its colour buffers; LOD sprites draw level 0, which takes the first) and the
  static colour per instance, but not checked against the console yet. The personal light (the lantern, `vi::tod::PersonalLight`,
  ramped as `SetupTimeOfDayLights` does) is the strip programs' point term;
  lighting is per vertex as VU1's (the game also tessellates near the point
  light, which is not done here). The two passes are the scene's: a material whose
  first layer is opaque draws whole at once, one whose first layer blends is
  deferred whole (`MaterialHasDepthSort`); the deferred pass runs in model
  order, not the game's tree-walk order (rooms, flora, actors): the flora after
  the zones and before the characters and the volumes, so only a zone's placed
  props' blended layers come before it, where the game draws them after.
- Zone streaming is `VIWorld::StreamLeaf`'s radial rule (load within 900 of a
  zone's bounds, let go past 950, a zone a frame, all at once under the loading
  screen) for drawing only: collision still loads the whole file (two seconds for
  Tunaria), and `VIZone::Stream`'s finer per-static radii (500/550) are not ported.
- A lighting band along terrain patch edges (zone 84 at x = 25000): not a gap,
  the edges' vertex colours or normals; to revisit with the real lighting.

## In a browser

The same client builds for `wasm32-unknown-unknown` and runs in a page
(`web/`): WebGPU where the browser has a working adapter, else WebGL2 (the
renderer asks for nothing WebGL2 lacks, and the adapter there is the canvas's
own, so the device is made on the page's canvas before the event loop). A
page on WebGL2 draws 30 frames a second (`web::frame_due`: an animation frame
before the next is due is skipped whole, the game's clocks seeing longer
frames; the options' Frame Rate, or `?uncapped`, lifts it). A browser
drawing without the graphics card (a software renderer, by WebGL's unmasked
renderer, WebGPU's adapter info or the client's adapter: SwiftShader, llvmpipe,
softpipe, lavapipe, a "Software" renderer, or Windows' WARP, "Microsoft Basic
Render Driver", F3 20261027-003944) is told so: on the gate's card with its
browser's steps, in a notice once, and on the status line in the world
(`web/main.js` `noteSoftware`, `web/pagetest.py` "software"); natively the log
says so (`gpustart::software`). The
player picks their own disc image in the page; it is read there a slice at a
time (`File.slice`), never uploaded, and nothing from it is served. With
"Remember my disc images in this browser" ticked (Chromium-based browsers,
which have the File System Access picker), a pick goes through
`showOpenFilePicker` and its handle, never the image, is kept in the origin's
IndexedDB: the next visit puts the image back in its input when the browser
still allows reading it, else offers it on a "Use <file> again" button whose
click asks, and Start asks for it in its own click; ticked after a disc was
picked the browser's own way, the picker opens at once to keep it (or a
"Remember <file>" button offers it); a dropped file's handle is kept too; a
file moved since is said so and forgotten, and unticking forgets both; a
report's `remember:` line says what is kept and what the browser answered
(`web/main.js`, `web/pagetest.py` "remember"). What the
game reads synchronously is fetched first; whatever walks the image (its
directory, a world file's record headers) runs against `iso::Sparse`, a cache
that answers `WouldBlock` for bytes it lacks and is filled between attempts
(`tests/sparse.rs`: the listing in 2 fetches, 128 KB, equal to the file's).

Beside the game's page the same build has `fxview.html`, the spell-visual
preview go-eqoa-server's GM panel frames on its Spell visuals page (`gm.preview_url`;
`crates/eqoa/src/fxview.rs`, `web/fxview.js`): a robed human casts a visual as
a server's 0x00B1 plays it (`spells::cast_of` reads the bytes, `spells.rs` plays
them on the two characters' own skeletons) at a training dummy (body 0x66262F1C
at its rows' size, 0.25), a second human or itself, again and again, under an
orbit camera; or (`both`) at a second human while a third, behind the caster,
casts it at itself in the same frame, so a visual's look on its caster and on a
target are seen side by side (two casts, not one at two targets: a cast's area
targets get only the events flagged for them). The panel hands it the six files it reads off the GM's own disc as
Blobs (opened on its own it asks for the image) and the visual by postMessage,
origins checked both ways (`https://gm.eqoaclassic.com`, or a loopback panel
named with `?panel=`); its host lets only the panel frame it. Natively
`eqoa fxview [visual [secs]]` is the same in a window and `eqoa fxview <visual>
<out.png> [ms,...] [secs]` draws PNGs (`EQOA_FX_AIM=caster|human|dummy|both`); off
the disc its test (`fxview::tests`) finds a visual that moves its caster and
shows particles and sees it cast again once nothing of it is left. Nothing
changes for a player who opens the game's page.

`spellfx.html` beside it is the community page that matches spells to their
visuals (`web/spellfx.js`; the user, 2026-10-26: "our community effort to help
match the spell fx to the correct spells", "a form that any player can fill
out ... no sign in gates"): every spell the server knows (go-eqoa-server's
account service, `GET /eqoa/account/api/spellfx/spells`), filtered by class, by
a search and by "still on a stand-in visual", and every visual on the player's
own disc, which the preview reads and lists (`fxview::visuals`, the
`started` message); a spell picked plays what it plays now as its own cast
(its cast time; a harmful one at a second human, the rest at the caster, or
what "Lands on" says, kept for the next visit: the caster and a second human
at once, a second human, the caster; never the dummy, whose quarter size
shrinks what lands on it), a visual tried plays as that spell's, W and S step
to the visual before and after from anywhere on the page (the preview too, not
while typing), and "This visual is <spell>'s" sends the pick with an optional name
and note (`POST .../suggest`; a pick for the same spell from the same place
replaces the last; GMs compare and accept them in the GM panel). The preview
is the build's own copy of `fxview.html`, framed on this origin and handed the
disc image as a File (`fxview-disc`); the image is never sent. A disc
remembered on the game's page is remembered here too (`web/discstore.js`, the
handles in IndexedDB both pages read). The lists scroll in their own boxes
beside the preview, which never moves away; on a phone it is held at the top.
`web/pagetest.py`'s spellfx checks hold the page's half to a stand-in server.

The page asks only for the player's disc image (the gate; the relay and the
offline viewer are folded under "Server and viewer"); Start runs the game from
its boot on the canvas, as natively: the loading screens, the licence, the title,
Station's login screen (sign-in and Create User Name are the game's own pages),
the news, the server list, character select and creation, the world. The
pregame's files are read off the image as each stage asks for them
(`pregame::files`), the world entry's in `world_library`'s order on a reader of
their own. A page can open neither a UDP socket nor a TCP connection, so the
session's datagrams (`net::session::Datagrams`: a UDP socket natively), Station's
connection (its login, account creation and password change) and the news
page's HTTP go through a relay, behind the pregame's `link`: go-eqoa-server's
`cmd/wsrelay`, which speaks eqoa-port's `tools/wsrelay.py` protocol, one
WebSocket for the DRDP datagrams and one per TCP connection (the relay must
reach the server's ports 9735 and 7000 for them). A server named by host name in
Network Setup is resolved by the relay; with none set, the page's own host is
the server. A world opens with its zones left on the disc and the ones round
the player read before the walk starts (`stream::fill_set`, awaited), the rest
as the walk comes near them (`web::disc::WebZones`, a `stream::ZoneSource`
whose reads finish on a later frame): in Freeport at the display's rate, 60
fps in Chromium, with 248 MB of wasm heap (the whole file read was 1.8 GB).
A world change (a teleport into another world, 0x00B2) is the same reads
(`stream::open_world`: the world file opened on a reader of its own and the zones
round the arrival read) while the old world plays on under the loading screen,
then the walk begins again there on the frame they are in: Lavastorm in 21-35 ms,
Tunaria with four zones in 260-400 ms, and back to 60 fps a second later. The
game's clock runs on through it, as VITimer does (the viewer used to restart it,
which put the creatures' animations before their start and panicked on a frame
of -1).

**A hidden page plays on.** A page behind another tab gets no animation frames,
and the browser holds its timers back (Chromium: to once a second, then about
once a minute after five minutes hidden), so the game stopped, its session sent
nothing, and the server let it go after its 50 pings: a tab left for eleven
minutes came back to "disconnected" (F3 20261025-175001). A worker's timer is not
held back, so while the page is hidden `web/tick.js` ticks at the game's 30
frames a second and each tick runs the frame an animation frame would
(`web::hidden_tick`, a user event on the event loop), the window counted as
covered: the game, its sound and its network go on and nothing is drawn, as a
covered window's frames natively (`HIDDEN_GAP`). Measured with another tab in
front: in Chromium 30.3 ticks a second through a 7-minute hide (no gap over 76
ms) while the page's own timer fell to about one a minute, in Firefox 30.1 (its
own timer at one a second); a page hidden for 12.5 minutes on a server with
eqoaclassic's settings kept its session, ran 30 frames a second, came back
where it stood and walked on, where the page before it was dropped 8.4 minutes
in and came back to "Connection problem" 30 seconds after it was shown; about a
quarter of one core while hidden. A page the browser freezes or discards (a
laptop asleep, low memory) runs nothing and still loses its session.

**The 2002 art in a page.** The form has a second, optional input for the 2002 disc
(EverQuest Online Adventures (USA), SLUS-20470), judged as it is picked by the
client's own rules (`web::disc_2002` over `era::judge_listing`) and read a slice at a
time like the first; like the first it is picked each visit. F9 with none asks for
it: the hidden input's picker inside the key's own activation, and a notice with
**Choose the disc** for a browser that opens no picker from a key; the swap goes on
once it is in. Its files come through one reader (`era::set_reader`, raw, by last
part: the world's stand-ins and the pregame's copies alike); the world loader and
the world opener take Tunaria off it with Frontiers' as its twin, and the zone
sources pick the image by the file's disc (`Library::era_of`). Swapping in Freeport:
its files, 112 MB, read in about 300 ms, the heap from 277 to 387 MB, a second at
about 46 fps (the containers open on the game's thread), then 60.
`?auth_port=`, `?game_port=`, `?patch_port=` and `?news_port=` point a page at a test
server's ports; `web/drive.py --iso-2002 <image>` puts the 2002 disc in the second
input, `--ask-2002 <image>` answers F9's picker with it, `--start-when line:<text>`
counts the script from a log line.

The start menu reads CLIENT's data and the HUD SUPPORT's, which the disc holds only
encrypted. The page unpacks both off the player's disc with `dnas`, each in a Web
Worker of its own (`web/unpack.js`) that instantiates the same compiled module, so
the game's thread never runs them: they start as soon as the disc is open and take
1.9 s and 2.7 s in Chromium, side by side (5.9 s and 6.3 s before the natives), and the frame rate stays at 60 while
they run. What they unpacked is kept in the origin's private storage (OPFS) under
the SHA-256 of `UTIL.REL` and the `.AUT`, so a later visit has both at once (a
page without `crypto.subtle`, plain http to another host, unpacks them every time).
On a first visit the HUD and the start menu come when they do, a few seconds into
the world if it was entered quickly.

```bash
cargo install wasm-bindgen-cli --version 0.2.129   # once: the version Cargo.lock pins
web/build.sh                                        # web/dist: the page, version.json and the build, v/<build>/
EQOA_WEB_DEST=user@host:/path/to/play/ web/deploy.sh
web/pagetest.py --iso run/eqoa.iso                  # the page's updates, reports and crashes (22 checks)
web/drive.py --iso run/eqoa.iso --view 'CHAR.ESF 0x70D898C6' --shot 6=human.png   # headless Chromium
web/drive.py --base https://host/eqoa/play/ --iso run/eqoa.iso --boot --keys 13=ArrowRight:100 \
    --keys 13.6=Enter:100 --keys 17=Enter:100 --type 21=<user> --shot 30=station.png
```

Each build is a directory of its own, `v/<build>/`, named by the digest of its files,
the page and the commit (`web/build.sh`), so nothing under that name ever changes: the
host serves `v/` as immutable and revalidates only the page and `version.json`.
`web/deploy.sh` publishes the build's directory first, then the page that names it, then
`version.json`. Builds stay two days, and the newest three always, for the pages still
running them: a page fetches its worker and its worklet a while after it opened. A page
already open asks for `version.json` every minute and whenever it is shown again. On the
gate with no disc picked it reloads at once; anywhere else it says a new version
is out and the player reloads when it suits them; a reload that brings the old page back
is a problem notice, not another reload. Until 2026-10-20 a deploy rewrote the files in
place one at a time: a page loaded during one could mix two builds (a tester's did, to
the second), and a tab left open never heard of a new build.

Problems are reported from the page (`web/report.js`) as the native client reports them
(`report.rs`, above). F3, the HUD's **Report a bug** under the target's bar, or a card's
**Report a problem** opens a dialog that sends a note, a picture of the frame (the client
says when its frame is drawn, `web::frame_drawn`), the client's state (`web::note_state`:
the character, the world, the entities round it, what has come of CLIENT and SUPPORT) and
the console's last 200 lines to the report server beside the page (`/eqoa/reports`); its
board is `/eqoa/reports/board`, linked from both cards. The account name and the password
are taken out of everything sent. A panic, a wasm trap or a lost graphics device stops the
client: the page opens the crash report (`/crash`), and a tab that died while it was shown
is offered on the next visit. What only takes a part away is a notice with a Send report
button: a disc other than Frontiers, named by the program it starts as soon as it is picked (`web/disc.rs`;
with the European discs and the Frontiers beta there is no HUD and no start menu, with
the first USA disc and the 2002 betas no world: each measured through the page), a
module that would not unpack on the Frontiers disc (unpacked once more past the page's
copy first), a file of the page that did not load, no sound, a failed world change.
`web/pagetest.py` checks the page's half against a stand-in for the report server: the
update paths, a report and its scrubbing, a crash, a tab that died while it was shown, a
page whose build is gone, the disc line, the full screen and the install. Each check has its control. `drive.py --scale`
is the display's own scale: at Windows' 125% and 150%, on WebGPU and on WebGL2, the HUD
draws as at 100% and the canvas holds the device's pixels.

Start (and View) put the page full screen in their own click (`web/main.js` "full
screen"; the user, 2026-10-27: "the browser build should force full screen, mobile
players cant figure it out", then "still allow f11 to non fullscreen"): the whole page,
not the canvas, so the notices, the report dialog and the phone keyboard's input stay
on it. On a phone or a tablet (a coarse pointer, `eqoaTouchFirst`) in any browser that
lets a page; one left (the back gesture, another app) comes back at the next touch on
the game, but not while an edit box has the keyboard (that touch puts it up). On a
computer only where Escape stays the game's: a browser ends a page's full screen on
Escape, and Chromium-based ones let the page keep it (Keyboard Lock: a tap is the
game's, held about a second and a half it ends the full screen, as the browser says on
entering; the game sees the held key's repeats), so Firefox's and Safari's stays F11's
alone, as before; and not with another window of the game open in the browser
(multiboxing: the windows side by side). A full screen asked for uses the click's
activation up, so Start with a remembered disc the browser must ask for first asks for
the disc and leaves the full screen to the submit, which gets it while the activation
lasts. F11 stays the browser's own: in a window its full screen, in any full screen (the
page's too) back to a window, Chromium taking F11 there before the page sees it. The
canvas cancels every key it is given (winit's listener calls `preventDefault`), which
kept F11 from the browser, so the page catches F11 on its way down and leaves it to the
browser; the canvas follows the window's size, and the HUD its shape. The canvas is the
visible area (`100dvh`): a phone browser's `100vh` is the height with its toolbars hidden,
which left the bottom of the game (the touch pad's lowest buttons) under them wherever the
page is not full screen (Safari on an iPhone, any phone browser before Start). iOS lets no page
on an iPhone go full screen (none in Safari 27's beta either), and an iPad's Safari ends
one at the first key typed ("Typing is not allowed in full screen websites"): there the
card says how to install the page instead. Natively Alt+Enter toggles full screen as
well; in a page it is the game's Enter, and the Extended page's Display is not there.
Checked headed on an Xvfb with a window manager, keys pressed through X (Chromium 154,
the game booted on SwiftShader): Start full screen with Escape locked, an Escape tap
reaching the canvas with the full screen kept, F11 to a window, to the browser's own
full screen and back, the canvas never seeing F11; before that, `drive.py --headed`
with F11 through X (the page 1192x609, then the screen's 1600x900, then back, the
canvas's buffer each time), and `--resize` (the game at 60 fps after each new size).
`web/pagetest.py` "fullscreen" holds the page's half. A report's `full screen:` line
says which rule held and what the browser answered.

The page installs as an app (the user, 2026-10-27: "we can add the install app feature
for each"): each build carries `manifest.json` (`display: fullscreen`, its `start_url`
and `scope` the page beside `v/`) and the program's drawn disc as PNG icons
(`tools/webicons`, made by `build.sh` off `icon_art.rs`: 192 and 512, a maskable 512
inside the circle every launcher's mask keeps, and iOS's opaque `apple-touch-icon.png`).
Started from the Home Screen or the apps it is full screen with none of the browser
round it, and its storage is the app's, so the modules unpacked off the disc stay
(Safari clears a site's after a week unused, not a Home Screen app's); it draws no
faster, the engine being the browser's. No service worker: Chromium 154 finds nothing in
the way of installing it without one (`Page.getInstallabilityErrors`). Chromium-based
browsers offer the install once the page has been used a little (`beforeinstallprompt`),
and the card's "Install EQOA as an app" asks for it; elsewhere the card says which menu
has it (iOS's Share menu, Firefox's on Android, any phone browser's, Safari's File > Add
to Dock on a Mac), and started as the app it says nothing (`web/pagetest.py`
"install"; a report's `app:` line).

The page takes `?relay=` and `?server=` (an IPv4 address; by default the
page's own host, as the relay resolves it), `?webgl` for WebGL2 where
WebGPU works (the same frame, 60 fps in Chromium through ANGLE) and `?padtrace`
(each pad key and gamepad event in the console). Not in the browser yet: a 3D
preview on the character screens; CHAR.ESF (148 MB) is still read whole.

A gamepad works in a page as natively (the page reads the Gamepad API itself,
`padmap`: every button and axis, and the layout each browser gives, Firefox on
Linux's own for an Xbox pad included; a pad shows up after its first button press,
as browsers expose them; `?padxy=swap` or `?padxy=keep` for a pad whose X and Y
the rule gets wrong), its
motors through the API's dual-rumble (`window.eqoaRumble`, main.js). On a phone or a
tablet (a page whose pointer is coarse, `window.eqoaTouchFirst`) the touch screen's
pad is there from the start. `drive.py` plays them: `--gamepad SECONDS=STEPS` (a
scripted pad behind `navigator.getGamepads`), `--mobile` (CDP's touch emulation),
`--touch SECONDS=STEPS` (CDP touch events on the canvas) and `--mouse SECONDS=STEPS`
(clicks, right clicks, the wheel, drags with either button, buttons held across steps). A
right click reaches the game: winit keeps the canvas's context menu shut. A drag in play
takes the Pointer Lock (asked for in the pointer's move past the slop, inside the press's
transient activation; after two refusals running, in the press), which headless Chromium
grants to CDP's mouse events; a browser keeps Escape to end its lock (the page sees it
gone), and an Escape that reaches the page lets go as well.

The sound is the native client's. A page can give the driver no thread of its own,
so it runs on the game's: once a frame (and at each animation frame a 30-fps page
skips) it is mixed up to the page's audio clock plus a lead and the frames are handed
to an AudioWorklet (`web/sound.js`) that only plays them, at 48 kHz (resampled where
the context will not run at that rate). The lead is what a sound the game starts
waits before it is heard, so it is sized by how far the audio clock moved between two
feeds over the last ten seconds (`audio::lead_for`: the third largest move, half again
and 5 ms, 30-300 ms); the clock moves in the blocks the browser's output takes (10.7
ms in Chromium, 30 in Firefox on Linux). Key to the worklet, in the world: 53-61 ms
median where it was 76-100 (and 150 in Firefox's first minute, its lead at 200). A
feed later than the lead leaves a short gap and pauses the driver for it, so nothing
is skipped. The AudioContext is made on the click that starts
the game (Start), as a page may only start sound from its user's gesture. The streamed music is read
whole off the disc (7 to 9 MB, 40-190 ms in Chromium) before the device starts it,
and the last three files are kept. In Chromium, in Freeport: 60 fps with the sound,
the region's music read and playing, no underrun after the world's first frames; the
status line shows the lead and the underruns, and `eqoaAudio.stats()` the worklet's
counts and level.
